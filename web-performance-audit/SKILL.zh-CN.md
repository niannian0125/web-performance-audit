从玩家能感觉到的一次操作查起。先说最值得修的地方，指出哪段代码在什么操作下多做了多少工作，以及怎样确认它已经修好。

## 怎么查

1. 读项目说明，找到操作入口、数据源及页面的创建与销毁位置。用户点名某个症状时，沿这条调用链查。全项目体检时，用下表覆盖适用项，合并同一根因。只有日志或代码片段时，标明可见范围。
2. 选择能反映症状的指标。例如每收到一条消息读取多少条记录、退出后每分钟还有多少次请求、导入时同时存活多少张位图。优先用项目现有测试或工具，在测试数据上取基线。记录环境、数据量和操作。能从源码证明的行为直接说明，真机耗时、内存峰值和崩溃原因各自需要证据。
3. 用户要求排查时，给出结论与复测办法。用户已要求修复时，执行范围内最小有效改动，沿原入口验证。保留收藏、聊天历史和跨页功能；涉及删除真实用户数据或不可逆迁移时，先征求明确授权。

## 八条经验怎么落到代码里

| 检查项 | 沿代码追到哪里 | 用什么判断 |
| --- | --- | --- |
| 1. 图片和音频存储 | 从写入追到读取、保留选项和过期清理。区分临时缓存、用户选择保存的原件、唯一副本以及其他记录共用的附件。 | 临时媒体是否持续增长？清理能释放哪些字节？清理后收藏和共用附件能否重新打开？ |
| 2. 图片压缩 | 分开看编码字节、实际像素、显示尺寸和解码耗时。聊天缩略图和点开看原图走哪条路径？按照片、文字、透明边缘和动图的画质需求选择有损或无损。 | 在目标尺寸看细节，记录读入字节和显示耗时。压缩能省空间；同尺寸改编码后，解码内存和速度要单独评估。 |
| 3. 数据库按需读 | 从列表、搜索、新消息等入口追查询范围、索引、排序、条数和触发次数，留意取全表后才筛选、排序、切片。区分热路径与一次性全量导出。 | 对比实际读取与显示的记录数，检查查询是否带出大附件。上翻历史时，同时间戳消息和不同会话的记录有无漏、重、串。 |
| 4. 上传入口限量 | 跟一批文件从选择、粘贴或拖入走到预览、解码和写入。检查单件字节、数量与总字节，以及像素数或音频时长；在能获得相应信息的最早阶段判断。 | 超限项能否在昂贵处理前被拦住或提示？后端接收时也检查其入口。按现有产品约束和设备实测定限额。 |
| 5. 聊天界面少渲染 | 分别查数据库读取、内存中的消息和实际挂载的消息节点。用分页或窗口化控制节点数量，保留上下缓冲和访问旧消息的入口。 | 新消息不断追加后，挂载数量如何变化？小心仅用 CSS 隐藏旧节点。验证上翻、异步图片撑高、滚动锚点和定位旧消息。 |
| 6. 懒加载与并发 | 顺着首屏导入、初始化和批处理队列追踪资源寿命。区分存储配额与运行内存。按需启动昂贵功能；按解码和处理峰值选择串行或有限并发。 | 记录同时在途任务和活跃的大对象。检查结果是否一直积存到整批结束，以及取消、失败、重试后的顺序和释放。 |
| 7. 毛玻璃与动画 | 在同一设备、同一段滚动或动画上，逐个切换模糊、叠层、动效和同时显示的大图。 | 比较帧耗时和卡帧，优先处理影响最大的效果。Android 宿主可按需请求刷新率；高刷缩短每帧可用时间，需以实际帧表现判断收益。 |
| 8. 幽灵后台任务 | 给计时器、轮询、监听器、观察器和动画循环找到所有者。沿离开、隐藏、卸载、重新进入以及异步完成路径追到停止或重新注册的位置。 | 反复进出后数活动任务和请求。页面级任务应随所属页面停下；音乐播放或番茄钟等跨页功能按业务结束条件回收。 |

需要设计测量或判断误报时，选读[复测场景](references/scenarios.zh-CN.md)中与操作对应的一节。

## 怎么交付

先给一句结论。每条发现写清 **优先级、文件与函数或行号、触发操作、代码证据、影响、建议和复测方法**。指出影响的是启动、空间、峰值内存还是交互帧耗时。优先处理有证据的崩溃、数据损失和高频入口卡顿。

用“代码已确认”“运行已复现”或“待验证”描述相应判断，注明已测的具体条件。没有设备时，可用计数器或已有测试验证工作量变化，把真机指标留作待测。修复后对比同一操作的前后结果，并交代相关功能回归情况。没有发现时，简述查过哪条路径及覆盖范围。
